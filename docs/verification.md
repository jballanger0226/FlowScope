# Verification status

Be aware of what has actually been exercised before relying on this in production.

## Run and passing
* Container behaviour under Docker (against the stand-in base above): the entrypoint fixing ownership of a named volume and of a root-owned bind mount, running with `--user`, health check, graceful stop on `docker stop`, data persisting across re-creation, CLI commands through the entrypoint, and NetFlow packets ingested over published UDP ports.
* Typecheck of server and web sources; the unit, API-integration and protocol tests (`npm test`) on Linux with Node 22.
* NetFlow v5, v9 and IPFIX decoding and the UDP collector, using packets built by `src/sim/packets.ts` (written from the protocol specifications, not captured from real routers).
* The UI in a real browser (Chromium via Playwright) against the demo network: every tab, role-gated views, certificate and authentication screens, sign-in and sign-out, and light, dark and system themes (Chromium only; Firefox and Safari were not checked).
* Storage: the same scenario suite (`test/scenarios.ts`) passes on SQLite and on ClickHouse (a local server; 25.8 earlier, 25.3 for the report-prefix cases), including report prefixes /0, /20, /27 and /32.
* Switch-port VLANs, LLDP/CDP neighbours, ARP (IPv4 and IPv6) and MAC-table readers: unit tests with in-memory tables, and end to end against the simulated SNMP agent (probe, host refresh, locating a host, removing a device).
* Links and QoS and multicast changes in Chromium against the demo: VLAN column, the interface search, input and output policies, hosts-on-port table, host finder, the multicast tree, and the custom report prefix.
* RADIUS and LDAP/Active Directory clients against small mock servers written for the tests.
* SAML: canonicalisation and signature checks cross-verified against fixtures produced by independent code (Python `lxml` / `cryptography`).

## Written but not run

* **Container image on a real base.** The Docker image was built and run with a Docker daemon, but registries were unreachable, so the base layer was a stand-in root filesystem labelled `node:22-slim`, with `node_modules` and `dist` built outside the image. Not exercised: the real `node:22-slim` base, `npm install` inside the build, and a multi-arch (arm64) build. The CI `docker` job is the real check.
* **Proxmox CT template (web-interface route).** `packaging/lxc-template` has never been built into a real template or imported into Proxmox. Registries and Debian mirrors were unreachable here, so the Dockerfile was only linted (`docker build --check`), the first-boot script was run on its own (password generation, the "already set" case, the marker), and the installer's template mode and `flowscope-ctl update` script were exercised with stub `npm`/`node` builds. Not exercised: the Debian package set, `systemctl enable` during the image build, systemd booting the exported filesystem, Proxmox accepting the file (upload, OS detection, root password and network setup by the wizard), and the update from GitHub. The `lxc-template.yml` workflow boots the filesystem under privileged Docker as a smoke test, but it has not run yet. Treat the first real import as the test and expect to fix things. The first real import reported only SSH listening and no web console. The most likely cause found by reading the unit file is `ReadWritePaths=` still forcing a mount namespace after the LXC drop-in switched the other sandbox options off; that is fixed and a `flowscope-ctl doctor` command was added, but the cause has not been confirmed from the container's logs.
* **Proxmox VE.** `packaging/proxmox/flowscope-lxc.sh` and `install.sh` have never run on Proxmox or on a Debian system: they were tested with stub `pct`/`pveam`/`systemctl` commands and a local source tarball, and checked with `bash -n`. * **ClickHouse beyond the test server**: other versions, clusters, TLS/auth setups, and large volumes.
* **ClickHouse as the default storage (packaging).** The backend choice logic (default, override, upgrade without data loss, waiting for a server that is still starting, falling back) has tests in `test/backend_default.test.ts`, run against a fake HTTP server standing in for ClickHouse. The Compose files were validated with `docker compose config` only and have not been started. The ClickHouse setup shared by the Linux and Proxmox installers (`packaging/linux/clickhouse-setup.sh`) and the template's first-boot user creation were run only against a scratch directory: the XML and the password hash were written and checked, but no real ClickHouse server read them. ## Not validated against real systems
* **TTL expired flag**: tested with built packets and demo data, on both storage backends. Not checked against real routers; devices differ in whether they export minimum TTL and in how they count ICMP errors they generate.
* **Catalyst 9300X service policy (inferred, not confirmed).** An interface service policy that did not appear was traced, from the MIB text, to three causes that are fixed: only the output direction was read and the 9300X attaches many policies as input; the direction column was not used for the bandwidth units; and a failure while reading the table was swallowed silently. The cause on a real 9300X has not been confirmed because no Cisco hardware was available. If a policy still does not show, the device's note on the Links and QoS page says what the QoS tables returned (empty table, or the exact error), which is what is needed to find the next cause.
* **Host tracking on Cisco Catalyst.** The per-VLAN reads (`community@vlan` for SNMPv1/v2c, context `vlan-N` for SNMPv3) follow Cisco's documented behaviour but were only tested with a fake table reader, because the simulated agent cannot emulate VLAN-indexed communities. The Q-BRIDGE `dot1qFdbId` is assumed to equal the VLAN id. Uplink detection and the confidence levels are heuristics checked against simulated switches only; expect to tune the address-count thresholds (30 on a trunk, 8 on a port-channel) on a real network.
* **Ports filled in on a followed stream, and neighbour links.** When an exporter reports no out (or in) port, the console fills it in from the other direction of the stream, then the CDP/LLDP tables, then host tracking, and marks it "worked out". Tested with fake tables and a built stream, not against a real Catalyst. A neighbour is linked to a polled device by management address (CDP) or by name (with or without the domain; two devices with the same short name are never linked), and its port by name (`Gi1/0/46` and `GigabitEthernet1/0/46` are the same). LLDP management addresses are not read yet, so an LLDP neighbour with a name unlike the device name in FlowScope is not linked.
* **Flows by port.** The store condition (one device, one port, entering/leaving/either, half records that report only one side, another device using the same port numbers) is a shared scenario run against SQLite and, in CI, ClickHouse; the page was driven in a browser against seeded flows (the five counts, directions, an unpolled exporter, selecting a flow to show the followed stream under the table, the port search and the Links button). Not checked: a real exporter's records. A switch that exports on input only shows only flows entering each port, so "leaving" can look empty on it.
* **VM appliance (OVA for VMware ESXi, qcow2 for Nutanix AHV).** `packaging/vm/make-ova.mjs` is tested (`test/ova.test.ts`): the archive layout and order, tar header checksums, the SHA-256 manifest, the disk stored unchanged, a well-formed descriptor, and the system `tar` reading it. The first-boot and console-notice scripts were run in a scratch directory. **Never run: `packaging/vm/build.sh`** (it needs Docker, loop devices and Debian mirrors, none of which exist where this was written), so the partitioning, the chroot package install, GRUB for BIOS and UEFI, and the conversion are untested. `.github/workflows/vm-image.yml` builds it, checks that the OVA's disk equals the qcow2's, and boots the qcow2 under QEMU with BIOS and then UEFI firmware (virtio disk, e1000 NIC, a NoCloud seed) and waits for the web console; **that workflow has not run yet**, and expect to fix things on its first run. Even a green run does not prove ESXi or AHV: the OVF descriptor (hardware version 13, LSI Logic SCSI, VMXNET3, `otherLinux64Guest`, vApp properties for host name and SSH key) was written from the OVF and VMware specifications and never imported into vSphere; the VMware guestinfo / OVF cloud-init data sources, VMware Tools, Prism's image upload and Custom Script (cloud-init) were not used. A one-time `root` password and the web `admin` password are shown on the console login screen (a root-only file); the screen drawing was not seen on a real console.
* **Kubernetes manifests.** `packaging/kubernetes` was checked for valid YAML, and the settings the pod uses (non-root, `FLOWSCOPE_HTTPS_PORT=8443`, the image's own `healthcheck` command) were run on a plain machine. They were not applied to any cluster, so scheduling, the volume's ownership with `fsGroup`, the exec probes, the kustomize patch for ClickHouse, the `$(CLICKHOUSE_PASSWORD)` expansion, the ClickHouse StatefulSet and the load-balancer behaviour (UDP, `externalTrafficPolicy: Local` keeping the exporter's source address) are untested, including on Tanzu and NKP.
* **Well-known port names.** `src/query/wellknown.ts` is a hand-written list of about 160 IANA-registered ports below 1024, not the whole registry (the registry could not be downloaded where this was written), cross-checked against the system `/etc/services`. A port with no entry still shows as its number, and a name the list does not have is rejected by the search with a message. Tested in `test/query.test.ts` and in a browser; the names were not compared with the current IANA file, so a few registered names may be missing or differ.
* **Cisco CBQoS**: OIDs and table indexing follow the CISCO-CLASS-BASED-QOS-MIB text and a simulated agent; not run against real hardware. Class names, nested policies and counter widths differ between IOS versions.
* **RADIUS / LDAP / Active Directory**: only against the mocks above, not against FreeRADIUS, OpenLDAP or a real domain controller.
* **SAML**: not tested with a real identity provider (Entra ID, Okta, ADFS, Keycloak...). The implementation is deliberately strict (see README) and may reject assertions that other products accept. Do not rely on it as your only way in; keep the break-glass administrator enabled until you have tested your IdP.
* **Cisco tables added from a real walk (CEF forwarding table, DHCP snooping, EIGRP, BFD, CISCO-IF-EXTENSION queue drops and resets, storm control, port security, process CPU, StackWise, ARP inspection, NBAR2, multicast interface load).** The readers are tested against rows cut from one walk of a Catalyst 9300 stack (`test/fixtures/*-c9300.json`), including raw-byte addresses, missing tables and counters that go backwards, and the screens were checked in a browser on demo data. Not checked: any other IOS release or platform (ISR, Nexus, IOS-XR), a live device, the poller scheduling of the new readers (the simulated-device tests do not run in the sandbox this was written in), failure states of the walked stack (it had no storm control hits, broken stack ring or down BFD session, so those are tested by editing rows), and large tables (the forwarding table is capped at 80,000 prefixes and ARP inspection reads the details of at most 60 VLANs). EIGRP peers listed are the formed ones only; a lost neighbour is absent rather than shown down. Not available over SNMP on that device: IGMP snooping table, flow export configuration, err-disable table.
* **Performance**: no sustained load test beyond the unit tests; ingest rates for SQLite are estimates.

## Known limits
* Dependencies were vendored from source for development because the package registries were unreachable; `package.json` lists only `net-snmp` and no lock file is included, so the first `npm install` resolves current versions.
* Switching storage backends does not migrate data. Existing installs are never switched automatically; a new default applies only to a first start.
* **SNMP diagnostics (device check and OID walk).** When there is no LLDP table, the check reads the device's process list and, if `lldpd` is running, says that lldpd is not connected to the SNMP agent (AgentX) instead of the generic "not published". Checked against a real OPNsense walk (lldpd running with "2 neighbors" in its process title and nothing under .1.0.8802) and in tests; the cure itself (lldpd `-x` plus `master agentx`) was not confirmed on that firewall. The check logic, OID validation, value formatting, the background walk jobs (limits, cancel, error part way, row cap, filter) and the four export formats are unit tested with in-memory tables and a fake client. The endpoints (permissions, input validation, a check, a whole-tree walk, paging, filtering and the four exports) are covered by the API test against the simulated agent. The browser page was checked against a mocked 60,000-row walk: the page holds 100 rows at a time. The walk uses GETBULK (GETNEXT for SNMPv1) and has not been run against a real OPNsense or Catalyst, so the speed of a full walk of a large switch is untested.
* **Flow explorer preview and paging.** The store query (`recent` and `offset`) is tested on SQLite in `test/scenarios.ts`, and the page was driven in a browser against 9,000 seeded records, with the full answer delayed so the "not everything has loaded" warning could be seen. The ClickHouse version of the same query is covered by the same shared test but was not run where this was written (CI runs it). Not measured: how much faster the first paint is on a large real database; the preview skips the Status (hop health) analysis, which is likely the larger saving, but no timing was taken.
* **Aruba Instant APs (Wi-Fi tables and the access point role).** Built from one real SNMP walk of an AP (ArubaOS 8.12.0.3, model 535, one AP, two radios, two SSIDs, 14 clients): the parser reads that walk correctly (checked against the numbers in it) and `test/wlan.test.ts` covers a hand-built table of the same shape, the storage and the role rule. **The column meanings were worked out by reading the values, not from Aruba's MIB file**, which was not available. Treat as confirmed by the values: AP name, model, CPU, memory, uptime; radio channel, client count and noise floor (published as a positive number, shown as negative dBm); client MAC, BSSID, IP, name, operating system, SNR and connect time. Treat as a reading that fits the data but was not confirmed: the "channel busy" columns (the 4 second and 64 second figures), the transmit power unit (shown as dBm), and which of each pair of client rate and byte columns is toward the client and which is from it (traffic and rate to the client are the first of each pair, as the numbers suggest for downloads). Not read because they could not be pinned down: the radio packet counters, a client's two remaining numeric columns, and the per-SSID counters (the interfaces already carry traffic through the normal interface polling). A 6 GHz radio reuses the low channel numbers, so its band is not told apart from 2.4 GHz. The SSID-to-interface link uses the name pattern `radioN_ssid_idM` and is only made when the device lists one AP, because every AP in a cluster uses the same interface names. Wi-Fi state is the latest read only, with no history, so there is no graph of channel busy over time. Not tried: a cluster of several APs, other Aruba models, or SNMPv3.
* **Wi-Fi tables of other vendors (UniFi, Ruckus, Cisco wireless controllers).** **None of these was run against a real device.** They were written from the vendors' published MIB definitions (UBNT-UniFi-MIB `.41112.1.6`, RUCKUS-ZD-WLAN-MIB `.25053.1.2.2.1.1`, CISCO-LWAPP-AP-MIB `.9.9.513`, CISCO-LWAPP-DOT11-CLIENT-MIB `.9.9.599`) and `test/wlan.test.ts` only proves the code reads the tables as the MIB describes them. What each one gives: **UniFi**: SSIDs with BSSID, channel, client count and power, radios with one channel-utilisation figure, model, IP and uptime; the MIB has no client table. **Ruckus**: access points (name, model, serial, IP, uptime, CPU) and WLANs with client counts; the client table of the ZD MIB could not be read from the definition available, so there are no clients or radios, and Unleashed's own system MIB (`.25053.1.15`) is not read. **Cisco WLC**: access points (name, uptime, CPU) and clients (MAC, IP, user name, device type, SSID, AP, connect time, rate); radios, per-client signal and per-client bytes are not read because the table columns could not be confirmed. Anything a device does not report is shown as a dash. Only devices whose sysObjectID is under 41112 or 25053, or a Cisco device whose description says it is a wireless controller, get these tables read. Please send an `snmpwalk` of each vendor to confirm the columns. Meraki, Cambium, TP-Link Omada, FortiAP and Cisco lightweight APs are classed as access points by their description but have no Wi-Fi section.
* **QoS re-marking verdicts.** The class match statements and set actions are read from CISCO-CLASS-BASED-QOS-MIB (`cbQosMatchStmtName`, `cbQosSetCfgTable`) and were checked by running the parser over the real walk of a Catalyst 3850 with AutoQoS (policies `AutoQos-4.0-Trust-Dscp-Input-Policy` and `AutoQos-4.0-Output-Policy` read as expected, class matches such as `dscp cs4 (32) cs5 (40) ef (46)` parsed to numbers). In that walk the set actions are table maps (feature bit set, value 0), so a value is never available and such a policy is reported as configured marking that cannot be checked. A `set dscp` with a number is compared with what was seen, but no real device in the walks had one, so that path is covered by the unit test only. Not read: the table maps themselves, police exceed/violate marking (`cbQosPoliceActionCfgTable`), and non-Cisco devices (OPNsense and others give no verdict, the flag stays red as before). Where the change is between two devices the verdict only looks at policies of devices that export flows. The list shows the verdict for the first 100 streams of a full (not preview) result; later rows keep the plain red flag.
* **Multicast state (routes, outgoing interfaces, IGMP receivers, PIM).** Built from one real full walk of a Catalyst 9300 stack (IOS XE 17.18.4, 1,465 routes, 2,912 outgoing-interface entries, 246 IGMP cache rows, 19 PIM interfaces, 2 PIM neighbours, 308 RP rows). The reader and the "where should this go" comparison are tested against a 25-route cut of that walk (`test/fixtures/mcast-c9300.json`), the API end to end (`test/multicast_api.test.ts`), and both pages in Chromium against responses captured from the real code on that data. Checked against the walk: the standard and Cisco route tables list the same outgoing interfaces, and every IGMP cache entry also appears in the outgoing list of its group. The Cisco rate (`ciscoIpMRouteBps`) is bits per second: it matches the route's octets divided by its uptime. **Not verified:** a live poll of a real device (the walk was replayed through a stand-in SNMP client), any router that is not a Cisco Catalyst, IPv6 multicast, and routers that publish PIM-MIB differently (the draft PIM-MIB used by IOS is read, not the later RFC 5060 one). The multicast tables are large, so each device is read on its own session every two minutes; the load on a router with tens of thousands of routes has not been measured, and routes are capped at 20,000 per device.
* **Multicast search, paging and host locations.** Walked switch has no IGMP snooping per-port table (no Q-BRIDGE group table, no snooping MIB, no multicast MAC entries; CISCO-IGMP-FILTER-MIB is configuration only), so receivers are the IGMP cache's last reporter per group and VLAN, placed by host tracking. Checked in Chromium against 130 demo routes: search by group, source host, reporter and interface, 25/50/100 rows per page, Next/Previous.
* **Class rates were bytes per second shown as bits.** Per-class Sent and drop rates now multiply bytes by 8 (SQLite and ClickHouse); unit test added.
* **Priority queue and multicast limits.** *Needs attention* now also lists an interface whose strict-priority class is sending at 80% or more of the rate it is limited to (cbQosQueueingCfgPriorityEnabled, column 4 of the queueing table, from the MIB definition; not yet confirmed on a real walk), and one where multicast takes 50% or more of the line speed (IPMROUTE-STD-MIB octet rates, so only on routed ports and VLAN interfaces; a layer 2 port has none). A priority class limited to a share of what is left over has no fixed rate and is not checked. Both limits are the `alerts.priority` and `alerts.mcast` settings.
* **Names of interfaces that are not listed.** Loopbacks, VLAN and tunnel interfaces on a switch are read but not listed; their names are now stored (`interface_names`) and used wherever an interface is named (multicast routes, flow paths, host locations), so none shows as `ifNN`. Multicast also asks the device for the ifName of each interface it mentions. Checked against GREEN-SW-2835H-RA, where ifIndex 78 is Loopback0 (type 24).
* **Multicast members collected over time.** The IGMP cache holds one reporter per group and VLAN, and the walked switches have no snooping table over SNMP (Q-BRIDGE multicast and static multicast tables empty on CHAMPION-SW-T202-RA-A). The cache's last-reporter column is read every 30 seconds and each reporter is kept in `mcast_members`. A group gone from the cache clears its hosts; a host not heard from for 30 minutes is dropped unless host tracking (ARP) still sees it, and none is kept past 12 hours. This finds hosts as they answer queries, so it fills in gradually and can miss a quiet host.
* **Hardware model and PIM mode flag.** The model is read from `ENTITY-MIB` chassis (class 3) and module (class 9) rows only, so fans, sensors and ports are never fetched; tested against a fake SNMP client (`test/entity.test.ts`), and shown in Chromium on demo data. **Not verified:** a real device's entPhysical table (some platforms leave `entPhysicalModelName` empty and only fill `entPhysicalDescr`, in which case no model shows). PIM mode comes from `PIM-MIB` column 4 (1 dense, 2 sparse, 3 sparse-dense) and route protocol 8/9; not checked against a real dense-mode or sparse-dense router.
* **PIM checks (mode mismatch, mixed modes, dense without an RP).** Rules tested on constructed state (`test/pimcheck.test.ts`) and seen in Chromium on demo data. The far end of a link is matched by the neighbour address against the other polled devices' addresses, which needs `ipAddrTable` to give the interface. **Not verified** on a real network; the rules come from how PIM dense and sparse mode behave, not from a captured fault.
* **IGMP queriers, rendezvous point mappings and RPF.** RPF columns (`ipMRouteRtAddress`, `RtMask`, `RtProto`, `DifferentInIfPackets`) are present in the real Catalyst 9300 walk and the reader is tested against it (`test/multicast.test.ts`); the walk had no `igmpInterfaceTable` or `pimRPSetTable` rows, so those two readers are tested on rows built from the MIB definitions (columns and index layout from RFC 2933 and RFC 2934), not from a device. **Not verified:** that IOS XE or NX-OS fills `igmpInterfaceQuerier`, or the RP set table, in the way the MIB describes; a router that publishes the RFC 5060 `pimGroupMappingTable` instead (which would also say how a mapping was learned) is not read. Snooping queriers (a switch acting as querier with no SVI) are not published over SNMP. Three more columns of the route table are read per poll, so the load on a router with tens of thousands of routes is higher; not measured.
* **RPF links and multicast loss on a link.** The link between two switches is found by matching the RPF neighbour address to the other polled device's addresses (`ipAddrTable` with its interface), so it works only when that device is polled and its address table gave the interface. Loss on a link compares the neighbour's multicast bytes out with this router's bytes in over the previous read; the two devices are not read at the same moment, so differences under 10% or 250 kbps, and neighbours sending under 500 kbps, are ignored. Tested on constructed state and in Chromium on demo data (both links followed). **Not verified** on a live pair of switches. `igmpInterfaceTable` was checked against real walks of a Catalyst 9300 stack and a second Catalyst (querier 0.0.0.0 means none; expiry 0 means this router is the querier). `pimRPSetTable` was empty on both, so the RP list there comes from `pimRPTable` per group.
* **NX-OS (Nexus 93180YC-FX3, 10.6(4)) compared with the readers.** A full walk of the switch (`test/fixtures/nxos-c93180.json` holds the multicast, IGMP, PIM, entity and IP counter rows). Found and fixed from it: PIM and IGMP interface tables list interfaces that are `notInService` (23 of 54 here), which were being counted as running, so only active rows are kept (PIM status is column 7); the RP set hold and expiry times are columns 4 and 5; and the switch publishes **no `IPMROUTE-STD-MIB`**, so there are no outgoing interfaces, incoming interfaces, rates or RPF. Its routes are taken from `pimIpMRouteTable` (group, source, and the shared-tree or source-tree flag) and the page says so. The per-group RP table is also absent, so a group's RP is the closest range in the RP set that covers it. Multicast load per interface comes from the IP counters (`ipIfStatsHCInMcastOctets` and `HCOutMcastOctets`), which also count link-local control traffic such as PIM hellos. The model reads correctly (`N9K-C93180YC-FX3` on the chassis row). Also seen: the switch has `CISCO-IGMP-SNOOPING-MIB`, which gives snooping settings and the querier state per VLAN, but no table of group members per port, so the full membership still has to come from the CLI. **Not verified:** loss and RPF checks on NX-OS, since there are no routes to compare.
* **Hosts that joined, from NetFlow as well as SNMP.** Reads protocol 2 flows to groups (224.0.1.0 to 239.255.255.255) from the device's own exporter over the last 30 minutes (and 5 for "recent"), plus flows to 224.0.0.22 to count version 3 hosts. Tested with a stand-in store (`test/igmp_flows.test.ts`) and in Chromium on demo flows. **Not verified on a real exporter:** whether a Catalyst or Nexus exports IGMP in its flow records at all (control-plane packets are often not in the flow cache), nor the effect of sampling. The walks of your switches show most interfaces running IGMP version 3, which this source cannot attribute to groups, so on those networks it may add little. The page says when it saw none, so an exporter that does not carry IGMP is visible rather than silent. NetFlow times are windows, not timestamps.
* **RPF drops: now against history.** `ipMRouteDifferentInIfPackets` counts packets that arrived on an interface other than the route's incoming interface, since the route was created. Its meaning comes from the MIB definition; on the walked Catalyst the column is filled and its values (50, 4, 120) are small against routes that are two weeks old. A warning needs the counter to grow between two reads (about every two minutes); otherwise it is shown as history. With equal-cost paths and multicast multipath, a router accepts a group on one path, so a few packets arriving on the other path are counted without being a fault.
